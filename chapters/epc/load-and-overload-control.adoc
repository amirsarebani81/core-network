=== Load and Overload Control

==== Technical Overview

GTP version 2 - Control plane (GTPv2-C) load control and GTPv2-C overload
control are optional, complementary features. Both features manage
signaling traffic between EPC control-plane nodes and help keep the
network stable.

Load control is a preventive mechanism. A node uses load control to
balance the distribution of new sessions across its peers, before an
overload condition occurs.

Overload control is a reactive mechanism. A node uses overload control to
reduce incoming signaling traffic, after the node already operates over
its capacity.

An operator can support load control and overload control independently
of each other, based on operator policy. Each node piggybacks its
`Load Control Information` (LCI) or `Overload Control Information` (OCI)
onto existing GTP-C request and response messages. This method avoids
extra signaling traffic. The computation and transfer of this control
information must not add significant load to the sending node or to its
peers.

Overload control must still let the network give preferential treatment
to emergency services traffic and to enhanced Multimedia Priority Service
(eMPS) traffic.

Load control and overload control apply over the S11, S4, S5, S8, S2a,
and S2b interfaces.

==== Load Control Procedure

Load control lets a node, typically the SGW-C or the PGW-C, advertise its
operating status to a peer, for example the MME, the SGSN, the Trusted
WLAN Access Network (TWAN), or the evolved Packet Data Gateway (ePDG).
The peer uses this status to balance the distribution of new sessions.

The node includes an `LCI` Information Element (IE) in its GTP-C
messages. The `LCI` IE carries the following parameters:

`Load Control Sequence Number`:: Sequences the LCI updates. This number
lets the receiving node identify the most recent load information.

`Load Metric`:: States the current load level, as a percentage from 0 to
100, where 100 means the node operates at maximum load.

`List of APN and Relative Capacity` (PGW-C only):: States the load
status for a specific Access Point Name (APN). The PGW-C includes this
list when it does not distribute its resources evenly across its APNs.

Load control operates at two levels:

Node Level:: Advertises the load of the entire node. This level helps
distribute sessions evenly across a cluster of gateways.

APN Level:: Advertises the load for a specific APN. This level applies
when a PGW-C allocates a separate resource pool to each APN. It stops the
network from selecting a node for a new session on an APN whose resources
are exhausted, even when the node has spare capacity overall.

==== Overload Control Procedure

Overload control activates when a node operates over its nominal
capacity and its performance degrades. The overloaded node instructs its
peers to reduce the rate of Request messages that they send to it.

The node includes an `OCI` IE in its GTP-C messages. The `OCI` IE carries
the following parameters:

`Overload Control Sequence Number`:: Differentiates between OCI
instances. This number lets the receiving node collate reports that
arrive out of order.

`Overload Reduction Metric`:: States the traffic reduction that the
sender requests from the receiver, as a percentage from 0 to 100. A
value of 0 means the overload condition ended.

`Period of Validity`:: States how long the overload condition stays
valid. When this timer expires, and the node received no new OCI, the
receiving node considers the overload condition ended.

`List of APNs` (PGW-C only):: States the APNs that are in overload, for
example because of a shortage in the IP address pool.

A node reduces traffic toward an overloaded peer through the following
mechanisms:

Message Throttling:: The reacting node reduces the number of Request
messages that it sends to the overloaded peer, in proportion to the
Overload Reduction Metric. The reacting node does not throttle Response
messages, to avoid unnecessary retransmissions.

"Loss" Throttling Algorithm:: The default throttling algorithm. The
receiving node discards a fraction of the Request messages. A common
implementation uses a statistical loss function to select the discarded
messages at random.

Self-Protection:: An overloaded node can still reject incoming requests,
as a fallback when peer throttling does not reduce the load enough. The
node rejects these requests with a cause value such as `GTP-C Entity
Congestion` or `APN congestion`.

==== Message Prioritization during Overload

An overloaded node processes messages in the following order of
priority, from the highest to the lowest:

. High Priority: Emergency services traffic and eMPS traffic.

. Establishment and Mobility: Initial attach, handover, and bearer
modification procedures. The node gives these procedures preference over
less critical signaling.

. Resource Release: Procedures that deactivate PDN connections or
bearers. The node can prioritize these procedures because they free the
node's resources.

. Message Priority Header: A GTPv2-C node that supports the optional
4-bit `Message Priority` field, in octets 1 and 12 of the GTPv2-C header,
uses this field to signal a relative priority value, from 0 to 15.

==== Implementation Requirements and Enforcement

Peer Discovery:: A node decides whether to use load control and overload
control, based on local configuration and operator policy. This decision
applies separately to internal interfaces and to roaming interfaces.

Homogeneity:: Operators must support these features consistently, across
all nodes in the network. Partial support can cause unfair load
distribution: supporting nodes throttle their traffic, while
non-supporting nodes keep overwhelming the target node.

Direct Enforcement:: A node enforces load control and overload control
for peers that it directly contacts, based on the metrics that those
peers report.

Remote Enforcement:: A node also enforces control for entities that it
does not directly contact, for example an MME that signals to a PGW-C
through an SGW-C. In this case, the source node enforces control based on
the maximum reduction metric that any node in the signaling path reports,
whether that node is the target or an intermediate node.

Interaction with the PGW-C Back-Off Timer:: For a given APN, a PGW-C must
use either APN-level overload control or the PGW back-off timer
mechanism. The PGW-C must not use both mechanisms at the same time.

==== Messages Carrying Load and Overload Control Information

A node includes the `LCI` IE and the `OCI` IE in a wide range of session
management messages, including:

* `Create Session Request` and `Create Session Response`.
* `Modify Bearer Request` and `Modify Bearer Response`.
* `Delete Session Request` and `Delete Session Response`.
* `Create Bearer Request`/`Response`, `Update Bearer Request`/`Response`,
  and `Delete Bearer Request`/`Response`.
* `Downlink Data Notification`.
* `Bearer Resource Command` and `Bearer Resource Failure Indication`.
